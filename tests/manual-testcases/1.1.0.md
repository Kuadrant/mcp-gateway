# Manual Test Cases — 1.1.0

## Observability

### Broker metrics scraped through a `port: metrics` PodMonitor

**Related PR**: Fix for [#1572](https://github.com/Kuadrant/mcp-gateway/issues/1572).

**Why manual**: The e2e CI environment does not run Prometheus Operator. This
scenario checks that Prometheus discovers the broker container's named `metrics`
port and scrapes it. The port declaration itself is covered by unit tests.

- [ ] Set up the local environment from the branch being tested and confirm the
  broker container declares `metrics` on port `9090`:
  ```bash
  make local-env-setup
  kubectl get deploy mcp-gateway -n mcp-system -o json |
    jq -e '.spec.template.spec.containers[0].ports[] | select(.name == "metrics" and .containerPort == 9090 and .protocol == "TCP")'
  ```

- [ ] Install Prometheus Operator:
  ```bash
  kubectl apply --server-side --force-conflicts \
    -f https://github.com/prometheus-operator/prometheus-operator/releases/download/v0.94.1/bundle.yaml
  kubectl wait --for=condition=Available deployment/prometheus-operator -n default --timeout=180s
  ```

- [ ] Create a `Prometheus` that selects `PodMonitor`s in `mcp-system`:
  ```bash
  kubectl apply -f - <<EOF
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: prometheus
    namespace: mcp-system
  ---
  apiVersion: rbac.authorization.k8s.io/v1
  kind: Role
  metadata:
    name: prometheus
    namespace: mcp-system
  rules:
    - apiGroups: [""]
      resources: ["pods"]
      verbs: ["get", "list", "watch"]
  ---
  apiVersion: rbac.authorization.k8s.io/v1
  kind: RoleBinding
  metadata:
    name: prometheus
    namespace: mcp-system
  roleRef:
    apiGroup: rbac.authorization.k8s.io
    kind: Role
    name: prometheus
  subjects:
    - kind: ServiceAccount
      name: prometheus
      namespace: mcp-system
  ---
  apiVersion: monitoring.coreos.com/v1
  kind: Prometheus
  metadata:
    name: prometheus
    namespace: mcp-system
  spec:
    serviceAccountName: prometheus
    podMonitorSelector: {}
  EOF
  kubectl wait --for=condition=Available prometheus/prometheus -n mcp-system --timeout=180s
  ```

- [ ] Apply the `PodMonitor` from the "Scraping the metrics endpoint" section of
  `docs/guides/opentelemetry.md`:
  ```bash
  kubectl apply -f - <<EOF
  apiVersion: monitoring.coreos.com/v1
  kind: PodMonitor
  metadata:
    name: mcp-broker
    namespace: mcp-system
  spec:
    selector:
      matchLabels:
        app.kubernetes.io/name: mcp-gateway
    podMetricsEndpoints:
      - port: metrics
        path: /metrics
  EOF
  ```

- [ ] Port-forward Prometheus:
  ```bash
  kubectl port-forward -n mcp-system svc/prometheus-operated 9091:9090 &
  PF_PID=$!
  ```

- [ ] Confirm there is one healthy target per broker pod, scraped at
  `<pod-IP>:9090/metrics` with `endpoint="metrics"`. The target can take up to
  a minute to appear. Repeat the command until it succeeds:
  ```bash
  POD_IPS=$(kubectl get pod -n mcp-system -l app.kubernetes.io/name=mcp-gateway -o json |
    jq -c '[.items[].status.podIP] | sort')
  curl -s 'http://localhost:9091/api/v1/targets?state=active' |
    jq -e --argjson ips "$POD_IPS" '
      [.data.activeTargets[] | select(.scrapePool == "podMonitor/mcp-system/mcp-broker/0")] |
      ($ips | length) > 0 and
      length == ($ips | length) and
      all(.[]; .health == "up" and .labels.endpoint == "metrics") and
      ([.[].scrapeUrl] | sort) == ($ips | map("http://\(.):9090/metrics"))'
  ```

- [ ] Confirm `up` is `1` for every broker pod. Prometheus Operator sets `job` to
  `<namespace>/<PodMonitor name>`, so the query only matches the `mcp-broker`
  targets:
  ```bash
  curl -s 'http://localhost:9091/api/v1/query' \
    --data-urlencode 'query=up{job="mcp-system/mcp-broker",endpoint="metrics"}' |
    jq -e --argjson ips "$POD_IPS" '.data.result | ($ips | length) > 0 and length == ($ips | length) and all(.[]; .value[1] == "1")'
  ```

- [ ] Clean up. The monitoring CRDs are left installed because other local
  targets, such as `make otel`, also use them:
  ```bash
  kill $PF_PID
  kubectl delete podmonitor mcp-broker -n mcp-system
  kubectl delete prometheus prometheus -n mcp-system
  kubectl delete rolebinding,role,serviceaccount prometheus -n mcp-system
  kubectl delete deployment,service,serviceaccount prometheus-operator -n default
  kubectl delete clusterrolebinding,clusterrole prometheus-operator
  ```

## Session Store

### Redis Sentinel and Cluster failover keep backend sessions

**Related PR**: Fix for [#1592](https://github.com/Kuadrant/mcp-gateway/issues/1592).

**Why manual**: e2e covers Sentinel discovery against a single Sentinel. A real
failover needs a multi-node Sentinel set and a sharded Redis Cluster, which are
too heavy for the e2e environment. Parsing, validation and env injection are
covered by unit and controller tests.

- [ ] Deploy a Redis Sentinel set (3 nodes, quorum 2) and a Redis Cluster
  (3 primaries, 3 replicas) in the cluster, then create one session store Secret
  per topology with the `mcp.kuadrant.io/secret: "true"` label:
  ```yaml
  stringData:
    CACHE_MODE: sentinel
    CACHE_SENTINEL_MASTER: mymaster
    CACHE_SENTINEL_ADDRS: <sentinel-0>:26379,<sentinel-1>:26379,<sentinel-2>:26379
    CACHE_PASSWORD: <redis-password>
  ```
  ```yaml
  stringData:
    CACHE_MODE: cluster
    CACHE_CLUSTER_ADDRS: <node-0>:6379,<node-1>:6379,<node-2>:6379
    CACHE_PASSWORD: <redis-password>
  ```

- [ ] Point an `MCPGatewayExtension` at each Secret with `spec.sessionStore.secretName`,
  scale its broker-router to 2 replicas, and confirm the startup log shows the mode:
  ```bash
  kubectl logs -n <namespace> deployment/mcp-gateway | grep "cache using external redis store"
  ```

- [ ] Initialize an MCP session (protocol `2025-03-26`) and call the `headers` tool of
  `mcp-test-server2`. Note the backend `Mcp-Session-Id` in the response content.

- [ ] Run `kubectl rollout restart deployment/mcp-gateway` and wait for the rollout.
  Call the tool again with the same gateway session: the backend `Mcp-Session-Id`
  must be unchanged.

- [ ] Sentinel: trigger `SENTINEL FAILOVER mymaster` from a Sentinel pod and wait for
  `SENTINEL get-master-addr-by-name mymaster` to change. Without restarting the gateway,
  call the tool with the existing session (same backend session) and initialize a new
  session (its keys appear on the new primary).

- [ ] Cluster: run `CLUSTER FAILOVER` on a replica of a primary that holds session keys
  (`DBSIZE` greater than 0). Repeat the existing-session and new-session calls.

- [ ] Delete the session store Secret, then delete one broker-router pod. The new pod must
  fail to start (`CreateContainerConfigError` or a crash with `invalid session store
  configuration`) instead of running with in-memory sessions. Recreate the Secret and
  confirm the pod recovers.
