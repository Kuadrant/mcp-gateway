### Broker Prometheus metrics (phase 3)

**Related PR**: [#1293](https://github.com/Kuadrant/mcp-gateway/pull/1293)
**Why manual**: Metrics endpoint requires a running cluster. Verifying correct Prometheus output format, label values, and gauge zero-out on server failure cannot be covered by unit tests alone.

**Prerequisites**: Docker, `kubectl`, `kind`, `helm`, `curl` installed and on `$PATH`. Repo checked out at the `feature/metrics-phase3` branch.

#### Step 0: Stand up a local Kind cluster with MCP Gateway

```bash
# From the repo root on the feature/metrics-phase3 branch.
# This creates a Kind cluster, installs Istio, builds the local image,
# deploys MCP Gateway and registers the everything-server as an upstream.
make local-env-setup
```

This takes ~5 minutes. When complete you'll see:
```
MCP Gateway is available at:
  http://localhost:9080/mcp
```

> **Important**: `make local-env-setup` uses `make deploy-gateway` which pulls a
> published image, not your local build. You must reload your local build after
> setup so the metrics server is present:
>
> ```bash
> make build-and-load-image
> ```
>
> This builds the image from the current branch and restarts the pod.

Verify the gateway pod is running with the reloaded image:

```bash
kubectl get pods -n mcp-system
# Expected: mcp-gateway-<hash>   1/1   Running
```

Confirm the `everything-server` upstream is registered:

```bash
kubectl get mcpserverregistration -n mcp-test
# Expected: everything-server   ...
```

#### Step 1: Verify the metrics endpoint is up

```bash
kubectl port-forward -n mcp-system deployment/mcp-gateway 9090:9090 &
curl -s -o /dev/null -w "%{http_code}" http://localhost:9090/metrics
```

- [ ] Returns `200`

#### Step 2: Verify Prometheus text format

```bash
curl -s http://localhost:9090/metrics | head -5
```

- [ ] Output begins with `# HELP` or `# TYPE` lines

#### Step 3: Verify all 5 metric families appear after server registration

Wait ~10s after applying an `MCPServerRegistration` for the first discovery cycle, then:

```bash
curl -s http://localhost:9090/metrics | grep -E "^(# TYPE|mcp_broker)"
```

- [ ] `mcp_broker_discovery_total` counter present with `status="success"` and correct `server_name`
- [ ] `mcp_broker_discovery_duration_seconds` histogram present
- [ ] `mcp_broker_tools_discovered` gauge present with value matching the server's tool count
- [ ] `mcp_broker_upstream_connection_failures_total` counter present (only appears after at least one failure — absence here is fine, verified in Step 5)
- [ ] `mcp_broker_tools_list_response_bytes` gauge present with value `> 0`

#### Step 4: Verify no double `_total` suffix

```bash
```

- [ ] Returns no output

#### Step 5: Verify gauge zeroes on server failure

Scale the upstream server to 0 replicas and wait for 3 consecutive health check failures (3× `--mcp-check-interval`, default 3 minutes — patch to `5s` for faster testing):

```bash
kubectl scale deployment everything-server -n mcp-test --replicas=0

# The broker's readiness probe returns 503 when no upstreams are healthy,
# so the pod will show 0/1 Running — this is expected, not a crash.
# Wait for the default health check interval (60s) for failures to accumulate,
# or patch the interval down first to speed things up:
kubectl set env deployment/mcp-gateway -n mcp-system MCP_CHECK_INTERVAL_SECS=5
# Wait ~20s for 3 consecutive failures (3 × 5s + backoff)
sleep 20

# Port-forward directly to the pod (deployment port-forward skips unready pods)
POD=$(kubectl get pod -n mcp-system -l app.kubernetes.io/name=mcp-gateway -o jsonpath='{.items[0].metadata.name}')
kubectl port-forward -n mcp-system pod/$POD 9090:9090 &
sleep 1
curl -s http://localhost:9090/metrics | grep -E "mcp_broker_(tools_discovered|tools_list_response_bytes|upstream_connection_failures|discovery_total)"
```

- [ ] `mcp_broker_tools_discovered{server_name="mcp-test/everything-server"}` drops to `0`
- [ ] `mcp_broker_tools_list_response_bytes{server_name="mcp-test/everything-server"}` drops to `0`
- [ ] `mcp_broker_upstream_connection_failures_total{server_name="mcp-test/everything-server"}` is `>= 1`
- [ ] `mcp_broker_discovery_total{server_name="mcp-test/everything-server",status="failure"}` is `>= 1`

#### Step 7: View metrics in Grafana

Deploy the OTel observability stack (Grafana, Tempo, Loki) and a minimal Prometheus that scrapes the broker:

```bash
# Deploy Grafana + Tempo + Loki
make otel
```

Wait for the observability pods to be ready:

```bash
kubectl wait --for=condition=Ready pod --all -n observability --timeout=120s
```

The broker metrics port is not on the Service (the controller owns and reconciles it).
Get the pod IP to scrape directly:

```bash
BROKER_POD_IP=$(kubectl get pod -n mcp-system -l app.kubernetes.io/name=mcp-gateway \
  -o jsonpath='{.items[0].status.podIP}')
echo "Broker pod IP: $BROKER_POD_IP"
```

Deploy a minimal Prometheus configured to scrape the broker pod IP directly:

```bash
kubectl apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-config
  namespace: observability
data:
  prometheus.yml: |
    global:
      scrape_interval: 15s
    scrape_configs:
    - job_name: mcp-gateway-broker
      static_configs:
      - targets: ['${BROKER_POD_IP}:9090']
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prometheus
  namespace: observability
spec:
  selector:
    matchLabels:
      app: prometheus
  template:
    metadata:
      labels:
        app: prometheus
    spec:
      containers:
      - name: prometheus
        image: prom/prometheus:latest
        args: ['--config.file=/etc/prometheus/prometheus.yml']
        ports:
        - containerPort: 9090
        volumeMounts:
        - name: config
          mountPath: /etc/prometheus
      volumes:
      - name: config
        configMap:
          name: prometheus-config
---
apiVersion: v1
kind: Service
metadata:
  name: prometheus
  namespace: observability
spec:
  selector:
    app: prometheus
  ports:
  - port: 9090
    targetPort: 9090
EOF
```

Wait for Prometheus to be ready:

```bash
kubectl wait --for=condition=Ready pod -l app=prometheus -n observability --timeout=60s
```

Add Prometheus as a Grafana datasource:

```bash
kubectl patch configmap grafana-datasources -n observability --type=merge -p '
{
  "data": {
    "datasources.yaml": "apiVersion: 1\ndatasources:\n  - name: Tempo\n    type: tempo\n    access: proxy\n    url: http://tempo:3200\n    isDefault: true\n    jsonData:\n      httpMethod: GET\n      nodeGraph:\n        enabled: true\n  - name: Loki\n    type: loki\n    access: proxy\n    url: http://loki:3100\n    isDefault: false\n    jsonData:\n      derivedFields:\n        - name: TraceID\n          matcherRegex: \"\\\"traceid\\\":\\\"([^\\\"]+)\\\"\"\n          url: \"$${__value.raw}\"\n          datasourceUid: tempo\n          urlDisplayLabel: View Trace\n  - name: Prometheus\n    type: prometheus\n    access: proxy\n    url: http://prometheus:9090\n    isDefault: false\n"
  }
}'
# Restart Grafana to pick up the new datasource
kubectl rollout restart deployment/grafana -n observability
kubectl wait --for=condition=Ready pod -l app=grafana -n observability --timeout=60s
```

Kill any existing port-forwards, then forward Grafana:

```bash
pkill -f "port-forward" 2>/dev/null; sleep 1
kubectl port-forward -n observability svc/grafana 3000:3000 &
sleep 2
# verify it's up before opening the browser
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000
# Expected: 200
```

Open http://localhost:3000 in your browser (no login required — anonymous access is enabled).

Navigate to **Explore** (compass icon in the left sidebar), select **Prometheus** from the datasource dropdown, then run these queries:

```promql
# Current tool count per server
mcp_broker_tools_discovered

# Discovery success vs failure rate
rate(mcp_broker_discovery_total[1m])

# p99 discovery latency
histogram_quantile(0.99, rate(mcp_broker_discovery_duration_seconds_bucket[1m]))

# Tools/list payload size per server
mcp_broker_tools_list_response_bytes
```

- [ ] Prometheus datasource shows as connected (green check in Connections → Data sources)
- [ ] `mcp_broker_tools_discovered` query returns a result with `server_name="mcp-test/everything-server"`
- [ ] `mcp_broker_discovery_total` shows both `status="success"` and `status="failure"` series
- [ ] `mcp_broker_discovery_duration_seconds` histogram query returns a p99 value

```bash
kill %1  # stop Grafana port-forward
```

### Router structured audit log for tool calls

**Related PR**: TBD (CONNLINK-1385)
**Why manual**: Verifying structured log output requires a running cluster and live tool calls. Log content/format can't be asserted in e2e tests.

#### Prerequisites

Kind cluster with MCP Gateway running and at least one registered upstream:

```bash
make local-env-setup
make build-and-load-image
kubectl get pods -n mcp-system
# Expected: mcp-gateway-<hash>   1/1   Running
```

#### Step 1: Tail router logs in a separate terminal

```bash
kubectl logs -n mcp-system deployment/mcp-gateway -c mcp-gateway -f | grep '"tool call"'
```

> The router and broker share a pod. The `grep` filters to audit entries only.

#### Step 2: Make a tool call

Use an MCP client or `curl` to call any tool through the gateway:

```bash
# Port-forward the gateway
kubectl port-forward -n mcp-system deployment/mcp-gateway 9080:9080 &

# Call any tool (replace TOOL_NAME with a tool from your upstream)
curl -s -X POST http://localhost:9080/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"TOOL_NAME","arguments":{}}}' | jq .
```

#### Step 3: Verify the audit log entry

In the tailed log window, you should see a structured JSON line like:

```json
{"time":"...","level":"INFO","msg":"tool call","user":"","tool":"TOOL_NAME","server":"your-server","status":"200","request_id":"...","session":"..."}
```

- [ ] `msg` is `"tool call"`
- [ ] `level` is `"INFO"`
- [ ] `tool` matches the tool name called
- [ ] `server` matches the registered server name
- [ ] `status` is `"200"` for a successful call
- [ ] `request_id` is non-empty
- [ ] `session` is non-empty

#### Step 4: Verify user identity is captured (with auth)

If running with an AuthPolicy (OIDC or API key), obtain a token and repeat the call with an `Authorization` header:

```bash
curl -s -X POST http://localhost:9080/mcp \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <YOUR_TOKEN>" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"TOOL_NAME","arguments":{}}}' | jq .
```

- [ ] `user` field contains the JWT `sub` claim (not empty)

#### Step 5: Verify non-tool-call requests produce no audit entry

```bash
curl -s -X POST http://localhost:9080/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | jq .
```

- [ ] No new `"tool call"` log line appears for `tools/list` requests

```bash
kill %1  # stop port-forward
```
